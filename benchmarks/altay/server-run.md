# Measured on a running server

The other two files in this folder measure Altay's chunk code from a CLI harness. This one runs the
actual server: the PocketMine PHP binary, a real world, terrain generated by the real generator on
real worker threads.

## Setup

The binary comes from `pmmp/PHP-Binaries` at `pm5-php-8.5-latest`, built with `./compile.sh -P 5`,
which produces PHP 8.2.30 ZTS with pmmpthread, leveldb, encoding, morton, igbinary, crypto and
OPcache — and OPcache enabled in the generated `php.ini`, as a real server runs it.

Two things about that build are worth writing down:

- `compile.sh` links chunkutils2 **statically** into the binary (`--enable-chunkutils2` with
  `--enable-static=yes`). A statically linked extension can't be swapped, so the line was deleted
  from `compile.sh` before building. The binary then has no chunkutils2 at all and each variant is
  loaded as a shared `.so` — one binary, three extensions, nothing else different.
- The build ends with `rm -r -f "$INSTALL_DIR/include"`, so `phpize` has no headers to build against.
  Rather than rebuild the whole thing, a plain PHP 8.2.30 was configured with `--enable-zts
  --disable-all --enable-cli` just for its headers. Extension ABI depends on the module API number,
  ZTS and debug flags, which all match (`no-debug-zts-20220829`). The extension's own 33 `.phpt`
  tests pass under the PocketMine binary, which is the proof that the ABI lines up.

`ChunkBench/` in this folder is the plugin that does the measuring. It orders generation of a 21x21
chunk square through `World::orderChunkPopulation()` — the server's own asynchronous pipeline, so
terrain is produced on worker threads and handed to the main thread through FastChunkSerializer
exactly as it is in play — then times serialization of the finished chunks and reads the process's
RSS. Build it into a phar, drop it in `plugins/`, and the server shuts itself down when it's done.

Six runs per configuration, medians. The world is deleted and regenerated for every run, from a
fixed seed.

## Results

441 chunks, PHP 8.2.30 ZTS, 4 async workers, OPcache on.

| | baseline | palette | full | palette | full |
|---|---|---|---|---|---|
| generate 441 chunks | 1.523 s | 1.497 s | 1.373 s | -1.7% | **-9.8%** |
| serialize 441 chunks | 6.61 ms | 5.92 ms | 5.60 ms | **-10.6%** | -15.3% |
| deserialize 441 chunks | 21.77 ms | 19.83 ms | 19.38 ms | **-8.9%** | -11.0% |
| server RSS | 284.2 MB | 284.6 MB | 280.7 MB | ±0% | **-3.5 MB** |

### These numbers are smaller than the harness's, and that's the point

| | harness | real server |
|---|---|---|
| generate | -20% | **-9.8%** |
| serialize | -25% | **-15.3%** |
| deserialize | -17% | **-11.0%** |

Generation is the clearest case. The harness times block writes into chunks and nothing else; a real
generator spends most of its time in noise functions and population, all PHP, none of it touched by
this work. The 20% the harness reports is the gain on the part of generation this changes; 9.8% is
what's left once it's diluted by everything else the generator does. Serialization shrinks for a
similar reason: real chunks carry more block data per palette entry than the synthetic ones, so the
word array copy weighs more and the palette weighs less.

The harness numbers are not wrong, they answer a narrower question. When quoting a figure, quote
this one.

### Memory

3.5 MB saved with 441 chunks loaded, against a server that already occupies 280 MB before the
terrain: 1.2% of the process. The saving is real and scales with loaded chunks, but a server's
memory is dominated by things this doesn't touch.

### On serialized output

The serialized size is identical between configurations, and varies slightly between runs of the
same configuration (10,353,885 to 10,366,318 bytes), including on the stock build. That's chunk
population being sensitive to the order neighbours finish generating, not a difference in what the
extension produces — the byte-for-byte equality of the format is established in `README.md`.

## CPU cost on this binary

Instruction counts re-measured on the PocketMine binary, same method as `cpu-cost.md` (spread
between repetitions: 0.00% to 0.10%).

| generate | chunk | 68,000,966 | 67,999,961 | 49,735,382 | ±0% | **-26.9%** |

| serializeTerrain, rich | chunk | 293,225 | 130,963 | 131,692 | **-55.3%** | -55.1% |

| block read | block | 1,611 | 1,611 | 1,175 | ±0% | **-27.1%** |
| block write | block | 1,905 | 1,905 | 1,380 | ±0% | **-27.5%** |
| clone | chunk | 104,279 | 104,278 | 60,150 | ±0% | **-42.3%** |

The palette encoding costs **436 instructions per palette plus 139 per entry** here, against 475 and
126 on PHP 8.5 — the same shape.

This table also prices the one regression: the full configuration spends **1,950 more instructions
per chunk** than palette-only on serialization, which is 24 calls to `getBlockLayers()` at **81
instructions each**. That is the native version building a fresh array of objects where the PHP one
returned the array it already held. It costs 1.7% of a chunk's serialization and is worth fixing by
caching the array, but it doesn't threaten the result.
